# Bolt JS 5.1.0 upstream parity contract

Audited 26 October 2026 against the pinned `@slack/bolt` **5.1.0** source commit [`ffbe0b6c03a6b1e16b3d5d3c5c9a8ab3effcbc1d`](https://github.com/slackapi/bolt-js/tree/ffbe0b6c03a6b1e16b3d5d3c5c9a8ab3effcbc1d). This is the exact baseline recorded by `typescript-api-catalog.json` and `scaffold-disposition.json`, rather than the moving `main` branch. It describes the upstream contract to compare, not a claim that every TypeScript export deserves a PHP counterpart.

## What constitutes useful parity

Thunder Bolt should match the capabilities PHP callers need to receive verified Slack deliveries, select and run handlers, acknowledge them correctly, authorize per installation, call Slack, keep scoped state, and survive common deployment models. It should preserve the *semantic* behavior of a Bolt feature where practical, while using PHP's native composition and hosting model.

It should not copy a Node object model merely to achieve matching names. A PHP web host already owns request routing, server lifecycle, logging, dependency injection and process supervision. The relevant seam is a verified incoming delivery and an outgoing response, not an Express `Request` object or Node `Server`.

## Priority requirements that are easy to miss

1. **Acknowledgement timing is part of compatibility.** Bolt’s default HTTP mode can acknowledge then continue processing. Thunder Bolt presently executes inline and makes users move slow work to a durable job. That is a defensible PHP choice only if the API makes the boundary clear and always permits a timely acknowledgement. A future asynchronous HTTP host adapter needs exactly-once acknowledgement, error ownership and cancellation semantics, not a `processBeforeResponse` flag copied in isolation.

2. **Failure hooks need delivery context.** Bolt distinguishes ordinary versus extended error handling and receiver-stage failures. A PHP equivalent should receive a redacted delivery identity, listener identity, acknowledgement state and throwable, then choose log/rethrow/response policy. A bare `App::error(callable)` is insufficient evidence of equivalent operational behavior.

3. **Static-token identity needs an explicit policy.** By default, Bolt verifies a fixed token and hydrates bot/user IDs through `auth.test`; it deliberately exposes an opt-out. Thunder presently relies on configured identity. Add an explicit, host-appropriate startup/health-check option (rather than hidden network I/O in a request path) so `ignoreSelf` and diagnostics have dependable identity data.

4. **Custom properties are a host integration seam.** Bolt lets an HTTP or Socket Mode receiver attach app-specific request data to every middleware context. Thunder already preserves regex captures in `Delivery::matches`/`constraintMatches` and HTTP retry information in `Delivery::metadata`; the remaining gap is a safe, typed adapter-owned custom-context factory rather than duplicate match or retry plumbing.

5. **Function workflow-token attachment should be configurable.** Bolt defaults to using the workflow token for function deliveries but allows `attachFunctionToken: false`, falling back to the authorized bot/user token. Thunder supports the token itself, but should expose the deliberate opt-out. Stronger cross-process terminal fencing remains a useful optional durability feature; it is not an upstream-parity shortfall because Thunder already guards duplicate and uncertain completion within a delivery.

6. **Add small listener conveniences only after the seams above.** Bolt’s `subtype` and `directMention` middleware are useful readable filters. They should be composable PHP helpers (not hidden special cases), with tests for message subtypes and mention parsing. `ssl_check` support is similarly a narrow compatibility addition.

## Explicit non-goals unless demand changes

- Express middleware, Node `http` server options, raw Node streams and AWS Lambda event/callback types.
- Re-exporting the entire `@slack/types`, `@slack/web-api`, `@slack/oauth` and `@slack/logger` type universes. PHP has its own typed Web API and PSR logging interfaces.
- `App::start()` and `App::stop()` as universal methods. In PHP-FPM there is no process to own; CLI Socket Mode/jobs do have workers and should keep their own lifecycle.
- Copying the in-memory conversation store's weak channel-only identity. Tenant, conversation and root-thread scoping is safer and is already a PHP advantage.

## Decision rule for the parent parity map

Mark a feature **implemented** only when its caller-observable behavior has source and behavioral-test evidence. Mark it **partial** when it accepts the same registration shape but lacks an important context, acknowledgement, error or lifecycle guarantee. Mark it **intentionally different** only when this note identifies the PHP seam that replaces it. Scaffold declarations and matching class names are not evidence.
